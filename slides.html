Item acceptance and current availability must be checked with the organization.

07 · SafetyDeterministic defenses were tested
Model output is not trusted automatically

Application rules guard feasibility and handoff actions.

Dates + transport

Non-overlapping dates and unconfirmed vehicle needs are marked incompatible before a reservation.

Quantity + status

Atomic availability checks prevent duplicate allocation; unavailable quantity returns HTTP 409.

Plan validation

Unknown record IDs, invalid quantities, and infeasible proposals are rejected against fresh database records.

Untrusted text + input size

Listing text is marked untrusted, contact strings are redacted, and oversized planner input is rejected before a model call.

09 · Limits and next stepsPrototype boundaries
A local class project, not an operating service

What needs confirmation before broader use.

Limitations

  • Fictional demo users and handoff records; no public deployment.
  • No measured student usability, actual reuse, waste reduction, or financial savings.
  • Pickup coordination is limited: the giver can agree to the recipient’s proposed date/time while accepting. Without agreement, people must coordinate outside the app; no chat or later rescheduling flow exists.
  • Swap Room hours vary; use Yale Connect. Private-housing graduate eligibility needs confirmation, and categories do not guarantee item acceptance.
  • ReStore bath-towel acceptance is unknown; exact Portkey billing and cache-write usage are unavailable.
  • One grounded plan and a four-case filtering ablation do not establish broad match quality.

Next steps

  • If independent student testing is conducted later, record the task, time, outcome, and feedback.
  • Confirm current program rules and donation acceptance with the relevant organization.
  • Review course-key billing if exact charges are needed.
  • Upload only report.html and slides.html to Canvas; a demonstration video is optional.
