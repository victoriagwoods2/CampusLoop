02 · MotivationProblem framing

A recurring transition problem

Moving creates two connected problems.

This project grew from my own experience moving repeatedly as a student: useful belongings can be left behind or discarded at move-out, while a student arriving later may spend money replacing similar essentials.

The two moments are separated by time, different schedules, and uncertain logistics. A listing alone does not tell an arriving student whether an item will still exist on pickup day, whether enough quantity remains, or whether someone without a car can move it. A need list alone does not show which nearby item is feasible to collect.

Moving out

Useful items need a next home.

Students need a clear way to describe condition, quantity, pickup deadline, and whether an item needs a vehicle.

Moving in

Essentials need a workable pickup.

Students need to compare items against arrival dates, availability windows, location, and transport limits before requesting them.

Product hypothesis

If a local tool joins listings and needs with deterministic timing and transport checks, then students may be able to identify workable reuse handoffs and clearer donation next steps. This is the hypothesis behind the prototype, not a measured impact claim.

Evidence boundary. One student tested the interface. Their comments describe hypothetical moving and reuse scenarios; they do not establish reduced waste, lower spending, carbon savings, or actual reuse outcomes.

03 · What is newExisting alternatives

A specific workflow focus

CampusLoop enters an existing reuse landscape.

Students already have community and campus options. Buy Nothing’s official site describes free giving and getting through its app and Facebook groups [1]. Yale Graduate Housing’s Sustainable Living page describes community programs including Spring Salvage [2], and a dedicated Swap Room page gives specific location and program information [3]. The Greater New Haven ReStore is another local option for donating goods [4,5]. CampusLoop complements these channels rather than claiming to invent student reuse.

04 · What is newInterface and scope

One clear starting point

Each page now starts with its own job.

The large hero and move-in/move-out cards are confined to Home. Find Items, Moving In, Moving Out, Handoffs, Donation Guide, and Project Evidence open directly on their own headings and primary actions. Project Evidence sits in secondary navigation.

Moving Out puts personal listings first and opens the form with Add an item; Moving In puts needs first and uses Add a request. Less common form fields sit under More details. Functional labels, buttons, and status text were enlarged while retaining the existing green/cream palette and typography.

Other refinements: plan cards are scoped to the signed-in user, direction, selected records, and unchanged record snapshot; edits make a prior plan stale. Handoffs emphasizes pending requests, accepted reservations, and completed pickups. Page counts now describe page-specific records.

Section 3 · Interface04 / 14
05 · Agent designArchitecture and tools

A bounded tool-using planner

The model proposes; application code verifies.

CampusLoop uses React/Vite, FastAPI, SQLite, and the Responses API through Portkey; PydanticAI is not in the runtime. One bounded agent suits this short, sequential task over shared records; multiple agents would have no independent subproblem. Application code rechecks proposed IDs and quantities, while reservation and pickup remain explicit user actions.

Model selection. I chose the course-key option, which requires gpt-6-luna through Portkey [9]. The assignment also permits other models with a personal key. The implementation pins this choice, and the saved real run succeeded; no comparative model-quality study was performed.

Implemented limitCode-level behavior
Model loopAt most 6 Responses API requests, 8 function calls total, and 700 output tokens requested per response. After 4 calls, the next request sets tool_choice="none" to require a final text response.
Timeouts25-second OpenAI client timeout; 0 automatic retries.
Plan inputAt most 10 listing IDs and 10 need IDs by request schema, with 20 combined in the shared validator. Context is capped at 800 characters by the schema and 3,200 UTF-8 bytes by validation.
Tool inputs/resultsID-array arguments allow at most 10 IDs; candidate listing/need tools return up to 20 records (database scans are capped at 40); donation resources return up to 10. Each JSON tool result is capped at 24,000 UTF-8 bytes.
Account rateAt most 5 planning runs per account in a rolling 24-hour window.

These are implemented limits from backend/agent.py, backend/core.py, and backend/app.py; they describe the current planner and are not a broader security guarantee.

The planner cannot reserve an item, agree an appointment, confirm a physical pickup, message anyone, or see secrets. Reservation and handoff writes use separate API routes and explicit account actions.
Section 4 · Agent design05 / 14
06 · Real run tracePortkey · gpt-6-luna

A saved successful planning run

One request found one grounded lamp match.

On 25 October 2026, the fictional incoming demo account selected its Lamp need. Plan 604fc8bd… completed through Portkey using only gpt-6-luna. All five provider requests succeeded.

  1. Read the selected need. retrieve_selected_needs returned the actual account request.
  2. Find candidates. retrieve_available_listings returned database inventory instead of invented items.
  3. Check feasibility. check_match tested the Floor lamp/Lamp pair against availability, dates, quantity, and transport.
  4. Validate the proposal. validate_proposed_plan checked record IDs and quantity against current records.
  5. Return an action summary. The plan said to review the details and request the item; it explicitly did not reserve it.
Grounding result. One feasible match; 0 unmatched selected needs; 0 clarifications. The rationale referenced a working lamp, East Rock, and overlapping dates/times present in the two records.

The plan’s temporary demonstration listing and need were removed after the evidence was saved, so the completed plan is now marked stale. This is a historical successful run, not a current reservation or a real exchange.

A separate successful tool trace invoked get_donation_resources during a move-out plan. It did not return a donation recommendation; a tool call is not proof an organization accepts an item.

Tools available to the planner

  • retrieve_available_listings returns available listings not ruled out by deterministic checks for selected needs.
  • retrieve_selected_listings reads selected move-out listings, their remaining quantities, and availability status.
  • retrieve_move_in_needs returns open requests not ruled out by deterministic checks for selected listings.
  • retrieve_selected_needs reads the signed-in planner’s selected open requests.
  • check_match checks one listing/request pair against recorded dates, quantity, status, condition, category, and transport.
  • get_donation_resources returns source-linked donation resources with their acceptance-verification status.
  • validate_proposed_plan checks proposed IDs and quantities against current records and deterministic feasibility rules.

A deterministic defense you can inspect

Feasibility checks run in application code.

Before a reservation is accepted, CampusLoop checks that dates overlap, quantity remains, the listing is available, and the transport requirement can be met. A plan validator also rejects invalid IDs, quantities, and incompatible proposals.

11 · Impact and metricsDonation alternatives

Source-backed guidance with uncertainty kept visible

The resource directory points outward; it does not promise acceptance.

The Habitat ReStore’s official acceptable-donations page says items must be in good, sellable condition and may be refused if unsafe, broken, unclean, or unusable. It lists lamps only when complete, working, and in excellent condition; it explicitly says ceiling fans are no longer accepted [5].

The list names wood and office furniture, chairs, tables, bookshelves, and bed frames, while excluding mattresses, box springs, toddler beds, cribs, and entertainment units. It lists small appliances under ten years old and in perfect working order.

For towels, the page excludes “linens (bed or table)” but does not name bath towels. Bath-towel acceptance is unknown; the app should not infer it from the broader exclusion.

Drop-off and pickup. The ReStore’s overview says small tools, dishware, and decorative items may be delivered during regular hours; the more detailed acceptable-donations page says drop-offs are by appointment during business hours. Because the official pages differ, contact the ReStore and arrange an appointment before traveling. Its page says pickups cover most New Haven County towns and also Clinton and Killingworth; exact town/service availability still needs confirmation [4,5].

Creator walkthrough — 26 October 2026

Observed by me: I could submit an item request and observe an accepted reservation; I was unsure where to find a specific pickup time; the completion-confirmation wording was confusing; and a success notification overlapped the navigation.

Fixes subsequently verified in focused local browser checks: accepted reservations distinguish a proposed time from an agreed appointment and show the available window and general area; completion buttons use role-specific physical-exchange wording; and success notices now sit below the header without covering navigation or content. 13 · Limits and next stepsSubmission status

Local prototype, not an operating service

Several questions need people and live sources.

  • No public deployment. The app runs locally at http://127.0.0.1:5173 and is not a Yale service. Demo accounts are fictional and are not verified students.
  • No live inventory. Listings, availability, pickup windows, and transport depend on user-provided records. The system does not calculate real routes or guarantee item condition.
  • Limited appointment coordination. A recipient may propose a pickup date/time; the giver can explicitly agree while accepting. Otherwise, the reserved card shows that no appointment is agreed and displays the listing’s availability window and general area. The app has no chat or post-acceptance rescheduling flow, so the people must coordinate any later change outside CampusLoop.
  • Donation research is partial. Yale Swap Room hours vary and current schedules are on Yale Connect; eligibility for graduate students in private housing needs confirmation, and listed categories do not guarantee each item is accepted. ReStore bath-towel acceptance needs direct confirmation; the City page was inaccessible.
  • AI evidence is narrow. One grounded successful plan and a four-case single-request comparison are not enough to estimate broad match quality. Model prompt-injection resistance was not tested live.
  • Token-cost evidence has a billing gap. Provider input, cached read, and output counts are logged; cache-write counts are not. Public OpenAI rates yield a reference range, not a Portkey account statement.
  • Limited usability evidence. One student tested the app and provided qualitative feedback; this single review does not establish broader usability.

Next submission work

  1. Test with additional students; record the task, completion time, outcome, and feedback with consent and no unnecessary personal data.
  2. Confirm private-housing student eligibility with the Swap Room and check Yale Connect for current hours and announcements; confirm each item before travel. Also confirm ReStore towel acceptance and obtain City item-specific recycling guidance.
  3. Upload only report.html and slides.html to Canvas. A demonstration video is optional; no separate URL, ZIP, PDF, or other files are required.
  4. Check course-key billing against the measured token log if exact account charges are required.
  5. The self-contained presentation is available in slides.html.

Design and feature scope are frozen. The items above are research, evidence, and course-submission follow-ups, not requests to expand this prototype now.
